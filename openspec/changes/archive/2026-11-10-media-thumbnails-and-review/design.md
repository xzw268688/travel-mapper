## Context

当前媒体链路：客户端把图片压到 1600px JPEG 后，用预签名 PUT 直传私有 OSS；`travel_note` 只保存 objectKey；读取时 `NoteService.signUrl` 为原图生成 600 秒预签名 URL，列表、详情、分享页都使用原图。`StorageCleanupService` 每日删除 24 小时未被引用对象。后台「可选 CDN 域名」配置存在但从未参与 URL 生成。视频接受 mp4/webm/mov 原样上传，没有转码。媒体审核只有事后的举报与管理员下架。

## Goals / Non-Goals

**Goals：**
- 列表、详情缩略网格与分享页加载小图，显著降低手机流量；历史数据自然回退原图。
- 为管理员提供可执行的媒体审核队列，不增加发帖前阻塞。
- MOV 上传前给出明确、可取消的提示。
- 不新增云服务费用，不显著增加 2C/1.8GB 服务器负载。

**Non-Goals：**
- 服务端 ffmpeg 转码、阿里云 MPS、自动图像/视频审核与 CDN 接入。
- 视频缩略图/首帧封面。
- 分享页视频展示、媒体审核通过后才公开。

## Decisions

### 1. 缩略图由客户端生成，服务端只签名

图片压缩后，前端用同一张 canvas 再生成 480px、JPEG quality 0.8 的小图（目标 ≤512KB）。通过 `POST /api/upload/presign` 新增可选 `thumbOf` 申请上传签名，服务端返回固定 Key `{原图 Key}.thumb.jpg` 并校验：`thumbOf` 必须以 `note/{当前userId}/` 开头、不含 `..`、内容类型为 `image/jpeg`、大小 ≤512KB。

- 为什么不在服务端生成：服务器只有 2C/1.8GB，Java 容器 640MB；保存游记时批量解码 20 张图会拉高堆与耗时。客户端已有压缩逻辑，顺手生成一张小图成本最低。
- 为什么不存映射表：Key 固定派生，读取侧无需查询；编辑/删除不需要额外同步。
- 代价：缩略图内容不受服务端校验（可能被恶意客户端替换）。小图仅用于展示，原图仍通过 `NoteMediaValidator` 校验；被替换的缩略图最坏只是显示异常，不影响内容与访问控制。

### 2. 读取侧无条件返回缩略图 URL，前端负责回退

`NoteDtos.ImageView` 增加 `thumbUrl`，`ListItem` 增加 `coverThumbUrl`，`SharePageResponse` 增加 `coverThumbUrl` 与 `imageThumbs`。服务端不 HEAD 检查缩略图是否存在，直接为 `{key}.thumb.jpg` 签名；历史游记没有缩略图对象时返回的 URL 会 404，前端 `@error` 回退原图，最后回退占位图。

- 为什么不在读取时 HEAD：列表一页最多 10 条，每条封面一次额外 HEAD 会放大 OSS 请求量与延迟；404 由浏览器缓存与回退处理更便宜。
- 详情大图/点击放大仍用原图，缩略图只用于列表、网格预览与分享页。

### 3. 孤儿清理必须识别缩略图

`StorageCleanupService` 当前只保留被 `images_json`、`videos_json` 或正文引用的 Key。缩略图不会被任何字段引用，若不处理会在 24 小时后被误删。清理判定增加：Key 以 `.thumb.jpg` 结尾时，去除后缀得到原图 Key，若原图被引用则保留缩略图；原图成为孤儿时缩略图一并删除。

### 4. 媒体审核采用「先发后审」队列

`travel_note` 增加 `media_reviewed_at`、`media_reviewed_by`。创建含媒体的游记时保持为空，游记按原可见性立即发布；`GET /api/admin/notes` 增加 `mediaReview=PENDING|REVIEWED` 筛选，列表返回 `hasMedia` 与 `mediaReviewedAt`；新增 `PUT /api/admin/notes/{id}/media-review` 标记已审核，写审计 `NOTE_MEDIA_REVIEW`。编辑游记时若 `images`/`videos` 实际变化，重置审核字段。无媒体游记不进入待审核筛选。

- 为什么不做先审后发：单人维护网站，管理员不可能随时在线；先审会让用户发完卡住。先发后审 + 抽查 + 举报下架是成本最低的闭环。
- 为什么用字段而不是新表：审核状态是游记的 1:1 属性，两列足够；历史游记默认待审核，管理员可按需清理。
- 代价：违规内容在管理员审核前可能已被看到；分享与举报通道仍提供兜底。

### 5. MOV 保留上传，增加确认提示，不转码

前端在选择 MOV（`video/quicktime` 或 `.mov`）后弹出确认框，说明 Android/Chrome 可能无法播放并建议导出 MP4；取消则不上传，确认后继续原流程。后端白名单与存储规则不变。

- 为什么不在服务端转码：2C/1.8GB 机器转 100MB 视频会长时间占满 CPU 与内存，且需要队列、状态、对象替换与失败重试，远超本期“代价最小”的范围。
- 为什么直接拒绝 MOV：iPhone 相册默认导出 MOV，拒绝会显著伤害主要的旅行记录场景；提示 + 允许上传保留兼容性，把选择交给用户。
- 服务端转码与阿里云 MPS 留作后续独立 change。

### 6. 不接 CDN

缩略图已把列表/网格流量降到原来的 1/10 左右；CDN 需要域名、备案或额外费用，且私有签名 URL 的缓存策略更复杂。本期不接入；后台「公开域名」配置继续保留，后续可单独设计。

## Risks / Trade-offs

- [客户端上传的缩略图不可信] → 仅用于展示，原图与访问控制不受影响；前端失败回退原图。
- [历史游记没有缩略图，首屏仍加载原图] → 回退逻辑保证可用；可在后续增加离线回填任务，本期不做。
- [缩略图对象数量翻倍] → 单图约 30–80KB，存储与请求数可控；清理任务保证孤儿不残留。
- [清理逻辑写错会误删缩略图] → 增加单元/集成测试覆盖「原图被引用则缩略图保留」「原图孤儿则缩略图删除」。
- [审核队列积压] → 先发后审不阻塞用户；管理员可按「待审核」抽查，违规用现有下架/举报流程处理。
- [MOV 仍无法在部分设备播放] → 上传前明确提示并提供取消；转码作为后续独立 change。

## Migration Plan

1. 执行 `V25__media_review.sql`：`travel_note` 增加 `media_reviewed_at`、`media_reviewed_by`（均可空，不改变既有数据）。
2. 部署后端：旧游记审核状态为空，进入待审核筛选；缩略图 URL 对旧游记返回 404，前端尚未更新时不受影响。
3. 部署前端：新上传图片同时生成缩略图；列表/详情/分享页优先小图并回退原图；MOV 确认框生效。
4. 回滚：回滚代码即可；新增列保留，旧代码忽略。已上传的 `.thumb.jpg` 对象可作为孤儿由后续清理任务删除（若回滚到未识别缩略图的清理逻辑，则会在 24 小时后清理）。
