## Context

本 change 建立在 change-01（表结构、配置中心、存储/搜索抽象）、change-02（JWT、额度与卡密）、change-03（城市字典、`trip` 归组、地图读模型）之上。行程生成是本项目最复杂的流程：涉及 LLM、搜索、Redis 缓存、额度扣减/退回、多城市分配和用户手动修改。所有表已由 change-01 创建，本 change 不新增表结构。

## Goals / Non-Goals

**Goals:**

- 用一次 LLM 调用同时产出按天行程与 `preparations`，并与搜索并行，控制首屏等待。
- 用“先扣后调 + 失败补偿 + 两段式去重”保证额度既不白扣也不双扣。
- 让用户在草稿态自由调整，保存时才落库并点亮地图。
- 让手动景点在重新生成时不丢失，且上限校验发生在扣费之前。
- 用标准化 SSE 事件和取消标志，统一“主动取消/断网/部分输出”三类额度边界。

**Non-Goals:**

- 不实现游记正文、图片上传、分享与记账（change-05）。
- 不实现草稿表；生成结果不落库。
- 不实现跨天拖拽手势（V2）。
- 不在本 change 引入工作流引擎、消息队列或多服务拆分。

## Decisions

### 1. LLM 通过 `LlmProvider` 抽象接入，LangChain4j 作为实现之一

业务层只依赖 `LlmProvider.generateItinerary(prompt)` 与 `polishStream(text)`，供应商、模型、密钥从 `sys_config` 读取。Prompt 强制“只输出 JSON”，返回后做 Schema 校验；失败重试 1 次，仍失败返回 `2012`。单次调用超时 30 秒。

**替代方案**：直接调用某家模型 SDK。被否决，因为需求要求后台热切换供应商（AC-04），直接依赖会把供应商写死在业务代码里。

### 2. 额度“先扣后调”，以 `requestId` 记录扣减来源

生成/润色开始前调用 change-02 的额度服务完成原子扣减，并记录 `{source, packId}` 与 `requestId` 归属。失败退回时读取该记录并删除标记，保证同一 `requestId` 只退一次。

**替代方案**：成功后扣费。被否决，因为并发与失败场景会让用户先用后欠，且需求明确要求后端先校验并拦截。

### 3. 生成去重采用“结果缓存 + 在途锁”两段式

指纹为 `sha256(countryCode | sortedCityCodes | days | normalizedPreference)`。先查 60 秒结果缓存；未命中则用 `SET NX EX 120` 抢在途锁；抢不到返回 `3001`；抢到则生成，完成后写结果缓存并在 `finally` 释放在途锁。

**替代方案**：只写结果缓存。被否决，因为两个相同请求并发到达时都会未命中，造成双扣。

### 4. 搜索与 LLM 并行，搜索独立降级

使用 `CompletableFuture` 同时发起 LLM 与 `SearchProvider.searchGuides`。搜索 5 秒超时后返回空列表，不阻塞行程；`guides` 缓存键为“国家 + 城市集合 + 天数 + 规范化偏好”，TTL 24 小时；搜索日上限默认 50，超限静默返回空列表。

**替代方案**：串行执行。被否决，因为搜索会显著拉长首屏等待，且需求要求搜索失败不阻断行程。

### 5. `preparations` 与行程同一次 LLM 调用，单独缓存

LLM 输出中同时包含 `preparations`，避免第二次调用。缓存键为“国家 + 城市集合”哈希，TTL 24 小时；缓存命中仍按一次行程生成扣费。

**替代方案**：独立生成接口。被否决，因为需求规定 `preparations` 与行程绑定、不可单独生成。

### 6. 多城市分配“校验 + 兜底”而不是直接报错

Prompt 要求按天分配且尽量连续；后端校验每天城市属于所选集合、天数足够时每个城市至少出现一次。校验失败重试 1 次；仍失败则回退为第一个所选城市的单城市生成，并写入 `warnings`，不退回额度。

**替代方案**：多城市失败直接返回错误。被否决，因为用户已经扣费且拿到不可用结果，体验与需求补丁都不允许。

### 7. 手动景点合并“先预校验、再合并、永不丢弃”

重新生成前，若 `keepManualSpots=true` 且现有手动景点已达 30，直接返回 `2006`，不扣费不调 AI。合并规则：同日同城追加；同日异城追加并提示；目标天不存在则追加到第 1 天并提示。合并后若总数超过 30，返回 `2006`，但此时 AI 已调用，额度不退。

**替代方案**：合并时丢弃超限景点。被否决，因为会静默丢用户数据。

### 8. 天数调整使用有序更新避免唯一键冲突

新增天时按 `day_index` 倒序后移，删除天时按正序前移，全程在单事务内完成，随后重算 `itinerary.start_date/end_date` 与所属 `trip` 的日期区间。修改某天城市不删除该天景点。

**替代方案**：先删后插重建所有天。被否决，因为会丢失 `dayId` 与景点排序，且并发风险更高。

### 9. SSE 使用 Spring MVC `SseEmitter` + 取消标志

润色接口返回 `text/event-stream`，按 `meta` → `delta`* → `done`/`cancelled`/`error` 发送。每个 chunk 前读取 `cancel:{userId}:{requestId}`；取消接口幂等且不泄露请求是否存在。Nginx 对润色路径关闭缓冲并延长读超时。

**替代方案**：引入 WebFlux。被否决，单体应用已有 Spring MVC + MyBatis，额外引入响应式栈收益不足。

### 10. 草稿仅存在于响应与前端状态

生成接口返回完整 DTO，不写 `itinerary` 表；保存接口负责校验与落库。这样草稿天然不点亮地图，也避免维护临时表与清理任务。

## Risks / Trade-offs

- **LLM 输出不稳定，JSON 可能缺字段或城市非法** → Schema 校验 + 重试 1 次 + 多城市单城市兜底 + `warnings`，并把模型选择放到配置中心。
- **并发相同请求导致双扣** → 在途锁 120 秒，抢不到返回 `3001`，锁在 `finally` 释放。
- **SSE 被代理缓冲，失去流式效果** → Nginx 关闭 `proxy_buffering`，集成测试断言首个 `delta` 在 1.5 秒内到达。
- **失败退回被重复执行导致多退** → 以 `requestId` 扣减记录为幂等依据，退回后删除记录。
- **合并手动景点时数据丢失** → 永不丢弃，按天/城市尽量合并，无法合并时放到第 1 天并提示。
- **搜索服务慢或不可用拖垮生成** → 并行 + 5 秒超时 + 空结果降级，不因搜索失败退额度。
- **天数增删触发 `(itinerary_id, day_index)` 唯一键冲突** → 倒序/正序更新 + 单事务。
- **缓存的 preparations 过期内容** → 24 小时 TTL，缓存与官方链接映射相互独立。
- **多城市回退后只覆盖一个城市** → 明确写入 `warnings`，前端提示用户可手动调整或分城市生成。

## Migration Plan

- 数据库结构已由 change-01 建立，本 change 无新增迁移。
- 依赖变更顺序：change-02 额度服务、change-03 城市/旅行服务完成后才能部署本 change。
- 部署后先用测试账号走通“生成 → 保存 → 地图变黄”，再开放给真实用户。
- 回滚策略：关闭生成/润色入口或切回旧配置即可；已保存行程数据保持兼容，无需回迁。
