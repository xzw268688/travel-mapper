## Context

本 change 建立在 change-01（表结构、存储抽象）、change-02（鉴权与行级隔离）、change-03（`trip` 归组、城市字典）、change-04（已保存行程与 `tripId`）之上。`travel_note`、`note_share`、`expense`、`exchange_rate` 已由 change-01 建表，本 change 不新增表结构。核心难点是富文本安全、分享链接的即时失效、汇率快照的历史一致性，以及前后端分离的海报生成。

## Goals / Non-Goals

**Goals:**

- 让用户在旅途中快速记录图文与消费，并自动归入国家/城市/旅行。
- 对外分享只暴露白名单字段，撤销/下架/注销后立即失效。
- 汇率变更不回溯历史，新增币种能自动纳入历史空快照。
- 海报完全在前端生成，后端不承担图片渲染成本。

**Non-Goals:**

- 不实现 AI 生成/润色（change-04）。
- 不实现真实支付、实时汇率或多币种账户。
- 不实现服务端海报渲染、视频、复杂排版。
- 不实现图片内容审核或人脸识别；仅做类型/大小与文本过滤。

## Decisions

### 1. 富文本存“已净化 HTML” + 纯文本摘要

前端使用 TipTap 产出 HTML，后端用白名单净化器移除脚本、事件属性、危险标签，再执行敏感词过滤；同时提取纯文本前 600 字存 `content_text`，供分享页取前 200 字。展示时不再二次信任客户端。

**替代方案**：存 Markdown 再渲染。被否决，因为需求与编辑器选型已锁定富文本 HTML，且图片混排更直接。

### 2. 图片直传对象存储，后端只发预签名

前端压缩并 canvas 重绘（天然剥离 EXIF GPS）后，用 300 秒预签名 PUT 直传；后端只校验 `bizType`、Content-Type 与大小。孤立对象由 change-01 的每日清理任务处理。

**替代方案**：图片经后端中转。被否决，2 核 4G 单机无法承受带宽与内存压力，且需求明确直传。

**已知限制**：后端无法二次验证 EXIF 是否已剥离，只能依赖前端流程；V1 接受该限制并在前端做强制压缩。

### 3. 游记/消费的国家、城市、旅行以“行程优先”

请求同时带 `itineraryId` 时，以行程的国家、城市、`tripId` 为准，忽略冲突入参；未带行程时，手动 `tripId` 必须与数据国家一致，默认选该国家最近一次旅行。复用 change-03 的归组服务，避免两套规则。

**替代方案**：完全信任客户端传值。被否决，会产生跨国家脏数据和汇总串账。

### 4. 分享令牌“一游记一活跃令牌”，撤销/下架即全撤

`note_share` 允许一篇游记有多条历史令牌，但有效令牌最多一条。创建分享时若已有有效令牌则复用；删除游记、下架内容时批量撤销全部令牌；恢复内容不复活旧令牌。令牌为高熵随机串并加唯一索引。

**替代方案**：每次分享都新建令牌。被否决，会导致旧链接长期可访问，撤销语义不清晰。

### 5. 分享页使用独立白名单 DTO，不复用抽屉接口

分享页只查 `travel_note`、`note_share`、`user`、`country`、`city`，返回固定字段；图片签名有效期取 `min(令牌剩余, 3600s)`。令牌不存在/撤销/过期、游记删除、游记下架、用户注销统一返回 `2007`，不泄露具体原因。

**替代方案**：复用国家抽屉或游记详情接口后裁剪。被否决，容易误带 `tripId`、旅行名称或花费。

### 6. 金额与汇率快照沿用数据库生成列

`amount` 与 `exchange_rate_snapshot` 使用 `DECIMAL`，`amount_cny` 为 STORED 生成列；API 金额使用字符串。保存消费时写入当前汇率值（不存 ID）；编辑时仅在币种或金额变化时重算快照，其余字段保留原值。汇总用手写 SQL，按快照折算并忽略 NULL。

**替代方案**：应用层计算 `amount_cny`。被否决，容易在编辑时漏更新，且汇总口径不统一。

### 7. 汇率新增与修改严格区分

`PUT /admin/exchange-rates` 在币种不存在时执行 INSERT，并在同一事务内回填该币种所有 NULL 快照；币种已存在时只 UPDATE 汇率表，不回填。回填条数作为 `affectedUnconfiguredRecords` 返回并写审计。

**替代方案**：每次修改都回填。被否决，会篡改历史事实，违反 BR-005。

### 8. 下架与软删除是两个独立状态

`takedown` 由管理员控制，`deleted` 由用户控制；两者任一为真都使分享页失效。下架时撤销全部分享令牌，恢复时只清 `takedown`，不恢复令牌。作者在 `deleted=1` 时不可通过恢复操作重新对外展示。

**替代方案**：复用 `deleted` 表示下架。被否决，会混淆用户删除与管理动作，也无法实现“本人可见但不可编辑”。

### 9. 海报完全在前端生成

前端用 `html2canvas` 截取隐藏 DOM 模板，用独立 Canvas 绘制国家点与时间顺序连线，用 qrcode 库生成指向分享页的二维码。生成前确保分享令牌存在并拉取地图统计；后端不参与图片渲染。

**替代方案**：服务端生成图片。被否决，单机资源有限，且需求明确前端生成。

### 10. 分享页不做服务端缓存

为保证撤销/下架/注销后立即失效，分享页查询不引入应用层缓存；图片仍使用短时签名 URL。若未来性能不足，可加“令牌版本号”后引入短 TTL 缓存。

## Risks / Trade-offs

- **XSS 过滤被绕过** → 使用成熟白名单净化器，禁止脚本/事件属性/危险协议，并加入 XSS 用例回归。
- **EXIF 未被可靠剥离** → 前端 canvas 重绘 + 发布前压缩；后端无法二次校验，作为 V1 已知限制记录。
- **分享令牌被猜测** → 高熵随机串 + 唯一索引；失效场景统一 `2007`，不泄露原因。
- **恢复内容后旧链接复活** → 恢复只清 `takedown`，不触碰 `note_share`；回归测试覆盖。
- **汇率回填误改历史** → 只在 INSERT 新币种时回填 NULL 快照，事务内执行并返回影响条数。
- **汇总性能随数据增长下降** → 使用 change-01 的 `(user_id, deleted, country_code, expense_date)` 等索引，手写聚合 SQL。
- **海报在部分浏览器渲染差异** → 使用 html2canvas + 独立 Canvas 绘制连线，避免直接截取复杂 SVG；提供失败提示。
- **图片直传后未发布产生孤儿对象** → 复用 change-01 的 24 小时清理任务。

## Migration Plan

- 数据库结构已由 change-01 建立，本 change 无新增迁移。
- 部署顺序：change-01 → 02 → 03 → 04 → 05；分享页依赖 HTTPS 域名，本地用局域网 IP + HTTP 验证。
- 上线前完成一次“发布游记 → 分享 → 撤销/下架 → 失效”的手工验证。
- 回滚策略：关闭分享与上传入口或回退前端版本；已保存游记/消费数据保持兼容，不需要数据回迁。

## Open Questions

无。图片内容审核、实时汇率与海报服务端渲染均明确属于 V2，不影响本 change 的规格与任务拆分。
